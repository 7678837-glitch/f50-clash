# ADR 0001：Mihomo 更新使用离线签名信任根

- 状态：已接受
- 日期：2026-07-20
- 决策者：xjoker（项目安全边界）

## 背景

f50mgr 以 root 运行。GitHub Release 的 digest 与资产来自同一仓库权限域，公司清单的
SHA-256 与资产来自同一服务器权限域；它们能发现传输损坏，却不能阻止账号或服务器被
接管后同时替换二进制和摘要。候选在 `mihomo -v` 阶段已经获得 root 执行机会，因此
ELF、版本和启动健康检查不能充当发布者认证。

## 方案比较

1. 继续信任 GitHub/公司摘要：实现最少，但网络源被接管即可远程 root 执行，不采用。
2. 完整 TUF：支持多角色、阈值签名和冻结防护，但第一阶段需维护多把密钥和元数据状态，
   超出单维护者项目的当前规模，暂不采用。
3. 离线 Ed25519 签名清单：把真实性信任根内嵌在 f50mgr，传输仍可用 GitHub 和公司镜像，
   实施与轮换边界清晰，采用。

## 决策

生产二进制只有在内嵌 keyring 中存在可信 Ed25519 公钥，且 detached signature 对清单
原始字节验证成功后，才能下载、执行或激活候选。公司 Basic Auth 只做访问控制，不能
在线下发自己的信任根；代码中不得出现 `allow_unsigned` 或等价旁路。

首个公开版本没有可安全托管的离线私钥，因此 keyring 为空，scheduler 固定报告
`disabled_no_trust_root` 并保留已安装 Mihomo。不得为了“功能看起来完整”在仓库、
GitHub Secrets、Actions Artifact 或设备上生成并保存长期私钥。

## 后续签名格式

签名清单应包含 schema、版本、架构、精确 HTTPS 资产 URL、大小、SHA-256、签发时间和
过期时间；`.sig` 包含 key id 和 Ed25519 签名。验证顺序必须是：查找内嵌 key → 验签
原始清单 → 解析清单 → 下载资产 → 校验摘要/架构/版本 → 事务激活与认证健康检查。

正常轮换先发布同时信任旧、新公钥的模块，过渡期清单双签；确认设备完成覆盖后再移除
旧公钥。私钥丢失或泄漏时停止在线签发，只能通过人工安装的新 Magisk 模块替换信任根。

## 结果

第一版牺牲无人值守更新，消除未经独立授权的网络源 root RCE。残余风险是离线私钥被窃、
合法签名版本自身含漏洞和源阻断导致冻结，分别由离线密钥卫生、人工审查和过期告警处理。
